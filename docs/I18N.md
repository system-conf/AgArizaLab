# AgArizaLab — i18n guide

Binding for every agent from v1.2 on (see `docs/PLAN_V2.md` §2). Libraries: `i18next`,
`react-i18next`, `i18next-browser-languagedetector`.

## 1. Files

```
src/i18n/
  languages.ts          the single language list { code, nativeName, dir }
  namespaces.ts         the namespace list (= JSON file names)
  typedResources.d.ts   CustomTypeOptions: keys typed from src/locales/en/*.json
  index.ts              initI18n, changeLanguage, currentLanguage, useLanguage (+ re-exports)
  localizedMessage.ts   translateMessage, translateList, useMessageTranslator
  messageKeys.ts        AppMessageKey type + localizedMessage() builder (no runtime deps)
  localeFiles.ts        import.meta.glob of the locale files (tr, en bundled; others lazy)
  LazyLocaleBackend.ts  i18next backend for non-bundled languages
  localeParity.test.ts  key / placeholder parity of every language against en
src/locales/<code>/<namespace>.json
```

Fallback language: `en`. Detection order: `?lang=` → localStorage (`agArizaLab.language`) →
browser; `tr-*` → `tr`, anything unsupported → `en`. The choice is persisted in localStorage and
`<html lang>` / `<html dir>` follow the active language. `main.tsx` awaits `initI18n()` before the
first render, so there is no flash of raw keys.

## 2. Using it in components

```tsx
import { useTranslation } from 'react-i18next'

function VerifyButton() {
  const { t } = useTranslation('exercise')       // namespace of your feature
  return <button>{t('verify')}</button>            // typed: a missing key is a compile error
}
```

- Other namespaces: `t('common:appName')`, or `useTranslation(['exercise', 'common'])`.
- Interpolation: `t('engine:unknownCommand', { command })` with `{{command}}` in the JSON.
- Plurals: keys `items_one` / `items_other`, call `t('items', { count })`.
- Numbers, durations, dates: `Intl.*` with `currentLanguage()` / `useLanguage().language`.
- Language switcher: `const { language, languages, changeLanguage } = useLanguage()` from
  `src/i18n`. Show `nativeName`; never translate language names.
- No user-facing literals in `src/features/**` or `App.tsx`: ESLint `i18next/no-literal-string`
  (`error`: lint fails on a literal). `title`, `aria-label`, `placeholder`, `label`, `alt` count
  as user-facing text too.
- User content (device names in labs, notes, lab titles) is never translated.

## 3. Classes, engine, session: return messages, not prose

Non-UI code never builds sentences. It returns codes (`FailureReason`) or a `LocalizedMessage`
(`src/domain/Messages.ts`):

```ts
interface LocalizedMessage { key: string /* 'namespace:path.to.key' */; params?: Record<string, string | number> }
```

Build it with the typed helper so the key is checked at compile time (type-only import of the
locale files, no i18next at runtime):

```ts
import { localizedMessage } from '../i18n/messageKeys'
return [{ kind: 'error', message: localizedMessage('engine:devicePoweredOff') }]
```

The UI renders it with `useMessageTranslator()` (hook) or `translateMessage(t, message)`. These
are the only places where a runtime key string meets the typed `t()`; the single cast lives in
`src/i18n/localizedMessage.ts`. Do not add other casts around `t()`.

### Terminal lines

```ts
type TerminalLine =
  | { kind: 'input' | 'output' | 'error' | 'info'; text: string; message?: never }            // device text
  | { kind: 'input' | 'output' | 'error' | 'info'; message: LocalizedMessage; text?: never }  // app message
```

**Device output stays English in every language**: Windows `ping` / `ipconfig` / `nslookup`
output and later IOS-style CLI output are `text` lines, exactly as real equipment prints them.
App text around it (`help` explanations, unknown command, device is off, no terminal on this
device) is a `message` line from the `engine` namespace and is translated.

## 4. Namespaces and ownership

Key naming: camelCase segments, nested by screen area, e.g. `complaintCard.title`,
`tabs.settings`. No sentences as keys, no dots inside segments.

| Namespace | Content | Owner (wave 1.1) |
|---|---|---|
| `common` | app name, language switcher, shared buttons/words | L1 |
| `landing` | landing / exercise list | L1 |
| `exercise` | exercise screen: header, complaint card, guide, verify footer | L1 |
| `results` | solution report screen | L1 |
| `device` | device panel leftovers: app link status, failure reasons, "saved" badge (settings: `deviceConfig`) | L2 |
| `map` | canvas cables (link lights, port labels) and React Flow screen-reader labels | L2 |
| `terminal` | terminal window chrome (title, clear, empty hint, labels) | L2 |
| `session` | failed-check descriptions and other session messages | L2 |
| `engine` | app-level terminal messages from the engine (help, unknown option, device off, no terminal) | E1 |
| `exercises` | exercise content (see §5) | X1 |
| `design` | design exercises: requirements, review, design UI | D0/D1 (requirements, review), D2 (ui, settings) |
| `designBriefs` | design brief texts per brief id | D3 |
| `simulation` | simulation UI, event list, PDU inspector, layer notes | K3 (frozen parts), S1 l1/l2, S2 l3, S3 services, U3 ui |
| `catalog` | device model names, port/medium labels | C1 (wave 2.1) |
| `workspace` | workspace canvas, palette, cable tool, annotations | B1 (wave 2.1) |
| `lab` | save / load / import / share messages, recent labs | B2 (wave 2.1) |
| `deviceConfig` | device settings and info panel (ports, host, VLANs, routing, services, wireless) | I2b (wave 2.2) |

Every agent may **read** any namespace but **writes only its own**, always in `tr` and `en`
together (the parity test fails otherwise). Placeholder keys created in wave 1.0 may be renamed or
removed by the owner.

## 5. `exercises` key layout

Exercise data (`ExerciseDefinition` in `src/domain/ExerciseTypes.ts`; the five built-in exercises are
still authored as v1 `V1ScenarioDefinition` in `src/scenarios` and migrated) holds topology, ids and
solve conditions only. All texts are keyed by scenario id:

```json
{
  "posGateway": {
    "title": "…",
    "complaint": { "from": "…", "message": "…" },
    "hints": ["direction", "location", "answer"],
    "explanation": { "whatHappened": "…", "realLife": "…", "interviewAnswer": "…" },
    "topics": ["…", "…"],
    "devices": { "<deviceId>": "display name", "…": "…" },
    "appLinks": { "<appLinkId>": "label", "…": "…" }
  }
}
```

- `hints`: exactly 3 items. `topics`: any count, same count in every language.
- `devices`: one entry per device id of the exercise network; `appLinks`: one per app link id.
  In the definition files `Device.name` / `AppLink.label` are placeholders (the id); the localizer
  fills them from these keys.
- Read arrays with `translateList(t, 'exercises:posGateway.topics')`; single items also work as
  `exercises:posGateway.hints.0`.
- `useLocalizedExercises()` (`src/scenarios/useLocalizedExercises.ts`, through `ExerciseLocalizer`)
  merges definitions and texts into the localized `Exercise` the UI consumes.

## 6. Adding a language

1. Copy `src/locales/en/` to `src/locales/<code>/` and translate every value (keep keys and
   `{{placeholders}}` unchanged).
2. Add one line to `languages` in `src/i18n/languages.ts`: `{ code, nativeName, dir }`.

Nothing else. Non-bundled languages are loaded lazily as separate chunks. `npm test` checks that
the folder and the list match and that every key and placeholder matches `en`.

Adding a namespace: add the JSON file in every language, the name in `namespaces.ts` and its type
in `typedResources.d.ts`.

## 7. RTL readiness

`dir` comes from `languages.ts` and is set on `<html>`. Use Tailwind logical utilities so layouts
mirror automatically: `ms-*` / `me-*` (not `ml-*` / `mr-*`), `ps-*` / `pe-*`, `start-*` / `end-*`,
`text-start` / `text-end`, `border-s` / `border-e`, `rounded-s-*` / `rounded-e-*`. Terminal output
stays left-to-right (`dir="ltr"` on the terminal), like on real devices.
